--------------------------------------------------------------------------------
1. HOW THE SYSTEM FLOWS  (end to end)
--------------------------------------------------------------------------------

  [ ESP32 + MPU6050 ]
        |  (Wi-Fi, HTTP REST)
        |  POST /api/v1/telemetry         <- raw sensor + posture samples
        |  POST /api/v1/devices/:id/heartbeat  <- every 15s
        v
  [ SmartPosture Backend  -- this server ]
        |  validation (Zod)  ->  services  ->  MongoDB (Mongoose models)
        |
        |  optional push (Socket.IO):
        |     "posture:update"   when new telemetry stored
        |     "device:status"    when a device goes online/offline
        |     "posture:alert"    when alert flag is true
        v
  [ Flutter mobile app ]
        |  reads dashboard / history / sessions / events / ai
        v
  [ Gemini AI  (optional) ] via POST /api/v1/ai/recommendations
        - only aggregated statistics are sent (never raw or personal data)


  Key behaviors:
    * Telemetry ingestion is IDEMPOTENT.
        - 1st time a sample is stored  -> HTTP 201
        - retry of the same sample     -> HTTP 200 (duplicate ignored)
      The dedupe key is: deviceId : ISO-timestamp : posture label : alert flag
    * Device online/offline is computed "on read" using a heartbeat timeout
      (default 60s, DEVICE_OFFLINE_TIMEOUT_SECONDS) plus a background sweeper.
    * Dashboard / Session durations are derived from TIMESTAMP DELTAS
      (never "1 sample = 1 second"). UNKNOWN posture is excluded from
      good/bad durations.
    * /health always returns 200 and reports REAL DB state ("ok"/"degraded").

4. SHARED ENUMS / CONSTANTS  (use exact strings)
--------------------------------------------------------------------------------

  posture.label          : GOOD_POSTURE | SLOUCHING | LEAN_LEFT | LEAN_RIGHT
                           | HEAD_FORWARD | UNKNOWN

  event.type             : POSTURE_INCORRECT | VIBRATION_ALERT | DEVICE_DISCONNECTED
                           | DEVICE_RECONNECTED | LOW_BATTERY | SENSOR_ERROR

  event.severity         : info | warning | critical
                           (default when omitted:
                              SENSOR_ERROR -> critical,
                              DEVICE_RECONNECTED -> info,
                              all others -> warning)

  device status           : online | offline | unknown

  period (dashboard / ai): day | week | month      (default = "day")

  list sort               : asc | desc             (default = "desc")

  pagination defaults     : page = 1 , limit = 20  (limit max = 200)

  deviceId rules          : 3..64 chars, only A-Z a-z 0-9 . _ : -
  timestamp rules         : ISO-8601 string, e.g. 2026-10-17T09:30:00.000Z
  Mongo id (path/param)   : 24 hex chars, e.g. 652f1a2b3c4d5e6f7a8b9c0d

[02]  INGEST TELEMETRY  (sent by the ESP32)
--------------------------------------------------------------------------------
  METHOD : POST
  URL    : {{baseUrl}}/api/v1/telemetry
  Auth   : none
  Body   : raw JSON (Content-Type: application/json)

  MINIMAL VALID BODY:
  {
    "deviceId": "posture-belt-01",
    "posture": {
      "label": "SLOUCHING",
      "angle": 28.4
    }
  }

  FULL BODY (all optional fields shown):
  {
    "deviceId": "posture-belt-01",
    "timestamp": "2026-10-17T09:30:00.000Z",
    "sensors": {
      "ax": 0.12, "ay": -9.71, "az": 1.03,
      "gx": 1.5,  "gy": 0.0,   "gz": -0.4
    },
    "posture": {
      "label": "SLOUCHING",
      "angle": 28.4,
      "confidence": 0.93,
      "badDurationSeconds": 12
    },
    "alert": false,
    "battery": 87,
    "samplingHz": 10
  }

  Field constraints:
    deviceId            : required (3..64, see rules)
    timestamp           : optional ISO-8601 (if omitted, server uses now)
    sensors             : optional | null
        ax/ay/az        : -160..160   (m/s^2, +/-16g)   each optional/nullable
        gx/gy/gz        : -2000..2000 (deg/s)           each optional/nullable
    posture             : required
        label           : required enum
        angle           : required, -180..180
        confidence      : optional 0..1 (nullable)
        badDurationSeconds : optional 0..86400 (nullable)
    alert               : optional boolean (default false)
    battery             : optional integer 0..100 (nullable)
    samplingHz          : optional positive number <= 200 (nullable)

  Success 201 (new record stored):
  {
    "success": true,
    "message": "Telemetry stored",
    "data": { "id": "<mongoId>", "duplicate": false,
              "sessionId": null, "events": 0 }
  }

  Success 200 (retry of identical sample -> ignored):
  {
    "success": true,
    "message": "Duplicate telemetry ignored",
    "data": { "id": "<mongoId>", "duplicate": true,
              "sessionId": null, "events": 0 }
  }

  Errors: 400 VALIDATION_ERROR | 429 rate limited | 500 INTERNAL_ERROR
          (503 DATABASE_UNAVAILABLE if DB down)

      * computes the current posture, distribution, average angle, posture

7. RECOMMENDED POSTMAN TEST SEQUENCE (happy path)
================================================================================

  1) GET  /health                                   -> expect status "ok"
  2) POST /api/v1/telemetry        (minimal body)   -> 201 Telemetry stored
     -> copy data.id  (use it in step 5)
  3) POST /api/v1/telemetry        (SAME body again)-> 200 Duplicate ignored
  4) POST /api/v1/devices/posture-belt-01/heartbeat -> 200 online, lastSeen
  5) GET  /api/v1/history?limit=5                   -> your record present
  6) GET  /api/v1/dashboard/current                 -> current posture
  7) GET  /api/v1/dashboard/summary?period=day      -> totals & distribution
  8) POST /api/v1/sessions         (deviceId)       -> 201 Session started
     -> copy data.id  (use it in step 9)
  9) PATCH /api/v1/sessions/<id>/end                -> 200 Session ended, final stats
 10) POST /api/v1/events           (VIBRATION_ALERT)-> 201 Event stored
 11) GET  /api/v1/events?type=VIBRATION_ALERT      -> event listed
 12) POST /api/v1/ai/recommendations  {}            -> 200 (or 503 if no API key)
 13) GET  /api/v1/ai/recommendations/live?deviceId=posture-belt-01
                                                    -> 200 advice for the last
                                                       10 min (source: gemini or
                                                       fallback; never persists)
 14) POST 2-3 more telemetry samples, repeat step 13
                                                    -> current posture follows
                                                       the newest real sample

  Negative / edge cases worth testing:
    - telemetry with angle=999            -> 400 VALIDATION_ERROR
    - telemetry with bad label "SIT"      -> 400 VALIDATION_ERROR
    - history with from > to              -> 400 VALIDATION_ERROR
    - GET /api/v1/devices/unknown-device  -> 404 DEVICE_NOT_FOUND
    - GET /api/v1/history/not-an-id       -> 400 VALIDATION_ERROR
    - very large JSON body                -> 413 PAYLOAD_TOO_LARGE
    - hammer /api/v1/ai/recommendations   -> 429 rate limited
    - GET .../recommendations/live?windowMinutes=0   -> 400 VALIDATION_ERROR
    - GET .../recommendations/live?windowMinutes=999 -> 400 VALIDATION_ERROR
    - GET .../recommendations/live (no telemetry)    -> 200 available:false
    - GET .../recommendations/live (old samples)     -> 200 stale:true

10.1  ROOT CAUSE - "the data is very sparse"
--------------------------------------------------------------------------------

  Diagnosis (not a patch):

  1. The ONLY AI entry point was POST /ai/recommendations with a whole-period
     window (day = rolling 24h, week/month = calendar). Statistics were built
     from that entire window, and the model itself was asked to judge density.
     A device that had been running for a few minutes therefore always looked
     "very sparse" even though its recent samples were perfectly usable.

  2. Storage and schema were verified and are CORRECT:
       - collection: telemetries (model Telemetry)
       - posture.label stored as the enum string, posture.angle as a number
       - timestamp stored as a real BSON Date (NOT a string)
       - index { deviceId: 1, timestamp: -1 } exists, so window queries are
         covered and sorted newest-first without a collection scan.

  3. deviceId filtering was correct (deviceId + timestamp range + sort + limit),
     and the dashboard and the AI path both read the same Telemetry collection,
     so there was NO aggregation mismatch between them.

  4. Timezone/timestamp handling was correct: timestamps are stored in UTC and
     compared as Date objects, so there is no local-time offset bug.

  5. No stale cache was hiding data: the cache only ever covered the historical
     day/week/month response, keyed by a SHA-256 statistics hash.

  Conclusion: the sparse warning was a real signal about the SHORT window used,
  not about lost data. The fix is to (a) analyse a short rolling window of real
  telemetry for live coaching and (b) report an explicit data-quality level
  instead of a vague "sparse" impression. No threshold was lowered and no data
  was fabricated.

--------------------------------------------------------------------------------
10.2  ROOT CAUSE - the /ai/recommendations/latest 404
--------------------------------------------------------------------------------

  NOT a missing route, NOT shadowing, NOT a wrong frontend URL, NOT a bad
  query filter. The route was registered, mounted and matched correctly.

  Actual cause (data deletion, not routing):
      In src/modules/ai/ai.model.ts the TTL index used
      expireAfterSeconds: AI_CACHE_TTL_SECONDS (300s). MongoDB therefore
      DELETED every successfully stored recommendation about five minutes after
      it was generated, so a later GET /recommendations/latest found nothing
      and correctly returned 404 RECOMMENDATION_NOT_FOUND.

  Fix (separate the two concepts that were wrongly merged):
      * Cache freshness - a stored recommendation is only REUSED while
        generatedAt is inside AI_CACHE_TTL_SECONDS. A stale-but-kept document
        no longer suppresses a fresh Gemini call.
      * Document retention - the TTL index now uses the new
        AI_RECOMMENDATION_TTL_SECONDS (default 2,592,000s = 30 days), so
        /latest keeps answering for a month.
      * MongoDB cannot alter index options in place, so syncRecommendationIndexes()
        (called once at startup) drops the legacy "recommendation_cache_ttl"
        index and then runs syncIndexes() to create "recommendation_retention_ttl".

10.4  HOW THE CURRENT POSTURE IS DETERMINED
--------------------------------------------------------------------------------

  1. Load the newest samples in the rolling window:
       filter { deviceId?, timestamp: { $gte: from, $lte: now } }
       .sort({ timestamp: -1 }).limit(AI_LIVE_MAX_SAMPLES), then reverse to
       chronological order (the oldest sample is the first element).
  2. currentPosture / currentAngle  = the NEWEST sample (index length-1).
  3. dominantPosture = the most frequent CLASSIFIED label. UNKNOWN is skipped,
     and ties are resolved by iterating POSTURE_LABELS, so the answer is
     deterministic. One bad reading is never reported as a trend.
  4. Durations come from TIMESTAMP DELTAS capped by SESSION_MAX_GAP_SECONDS
     (never "1 sample = 1 second"). UNKNOWN is excluded from good/bad time.
  5. persistentIncorrectSeconds walks backwards from the newest sample while the
     posture stays incorrect, and stops at a gap larger than the cap, so an
     offline period is never reported as one long slouch.

--------------------------------------------------------------------------------
10.5  HOW LIMITED DATA IS HANDLED  (dataQuality)
--------------------------------------------------------------------------------

  none        0 samples            -> available:false, source:"none", advice null
  limited     < 5 samples          -> a rough impression only; the summary says
                                      "That is a limited snapshot, so no
                                      long-term trend can be established yet."
  recent      >= 5 samples         -> a valid recent snapshot; still no long-term
                                      trend claimed
  established >= 60 samples AND
              >= 300s coverage     -> a trend may be discussed

  A full day is never required, and `source:"none"` is an explicit empty state
  rather than a crash or a fabricated reading.

--------------------------------------------------------------------------------
10.6  HOW THE GEMINI FALLBACK WORKS
--------------------------------------------------------------------------------

  The key stays on the backend only and is never exposed to the mobile app;
  only aggregated numbers are sent (no raw sensor stream).

  Order of resolution for /live:
      1. no samples                  -> source:"none"
      2. stale telemetry             -> source:"fallback" (no Gemini call)
      3. cache hit for the exact
         window + newest timestamp   -> cached:true
      4. Gemini configured           -> source:"gemini", validated JSON
      5. Gemini missing / timeout /
         rate limit / bad JSON       -> source:"fallback"
  The fallback is COACHING_BY_POSTURE: title + immediateAction + futureImpact +
  priority per posture (GOOD_POSTURE, SLOUCHING, LEAN_LEFT, LEAN_RIGHT,
  HEAD_FORWARD, UNKNOWN). Wording avoids medical promises - no claim of injury
  prevention or pain relief.

  Caching rules:
      * a live answer is cached IN MEMORY only (never written to MongoDB)
      * the key contains the newest sample ISO timestamp, so a new sample
        invalidates it immediately
      * TTL is short and configurable (AI_LIVE_CACHE_TTL_SECONDS)
      * identical statistics reuse the historical cache for day/week/month;
        refresh:true bypasses it
      * every cached response reports cached:true plus its generatedAt
